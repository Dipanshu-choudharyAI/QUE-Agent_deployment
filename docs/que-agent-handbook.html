Orientation

Overview

What QUE is, what it refuses to be, and how this document is meant to be used.

Quizzer is the product: users create quizzes and exams, take them, get graded, and review performance. QUE Agent is an independent AI microservice that gives Quizzer an intelligence layer, scoped to what Quizzer's users actually need — not a general-purpose chatbot wearing a Quizzer skin.

Every capability QUE has traces back to one of five things: answering questions grounded in real documentation, understanding where the user currently is in the product, reading real Quizzer data through controlled tools, chaining tool calls when a question needs more than one fact, and behaving differently by role because permission is a security boundary, not a UI convenience.

Governing principle

Do not add technology because it is popular. Add a component because it solves a measurable production problem you have already observed. Every phase answers: what breaks without this, and how would you know?

This document is two things at once: a curriculum, read top to bottom once, and a working project tracker, returned to as you build — task checkboxes, decision records, and the scorecard all persist locally so the document reflects the actual state of your build, not just your reading progress.

Why it matters

An LLM should never be your authorization system. It can recommend or request an action, but it never has final authority over authentication, authorization, or security decisions — that authority lives in Quizzer's backend, behind a controlled tool call, not in a database connection the model can reach directly.

AVOID
LLM → Direct SQL Access → Production Database
PREFERRED
LLM → Tool Call → Validation → Authorization
    → Quizzer API → Backend Logic → Database

Before writing a line of QUE, make sure the surrounding fundamentals aren't what actually slows you down.

0 / 0 tasks
LEARN→IMPLEMENT→TEST→MEASURE→DOCUMENT→SHIP

Objective

Get comfortable with the systems concepts every later phase assumes, so a systems bug never gets misdiagnosed as "the model is hallucinating."

Concepts to Learn

Backend & web
REST APIs, HTTP semantics, JSON, request/response lifecycles.
Auth & data
Authentication vs. authorization, JWTs/sessions, relational databases and indexes.
Systems
Docker fundamentals, microservice boundaries, sync vs. async I/O.

Tokens, context windows, inference cost — an LLM call is a network request, not a function call.

Phase 1 — QUE Core + Basic Observability + Basic Evals

The smallest thing that deserves to be called QUE: identity, scope, request understanding, and just enough instrumentation to know when it's wrong.

0 / 0 tasks
LEARN→IMPLEMENT→TEST→MEASURE→DOCUMENT→SHIP

Objective

Stand up a single service that receives a question, classifies it, and either answers from the model's general product knowledge or declines — with every decision logged from day one.

Why Now

Scope discipline is cheapest to build first, before RAG output and tool output compete for the model's attention. And observability/evals started here — not bolted on in Phase 11/12 — means you have a baseline to compare every later phase against.

What You Will Build

  • A /chat endpoint with a scoped system prompt and explicit refusal behavior.
  • A Request Understanding layer that classifies every incoming message before it reaches the model.
  • Structured request logging: request ID, latency, model, token usage, scope decision, errors.
  • A first golden set of scope/identity evals.

Concepts to Learn — Request Understanding Layer

Formalize the question "what kind of request is this?" into an explicit step, run before routing to RAG, tools, or a plain model answer:

USER REQUEST
    │
    ▼
REQUEST UNDERSTANDING
    ├── Scope        (in-domain? out-of-domain?)
    ├── Intent       (knowledge / analytics / action)
    ├── Risk         (read / low-risk write / high-risk write)
    ├── Freshness    (static / dynamic / critical)
    ├── Data Req.    (none / knowledge base / live tool)
    └── Complexity   (single-step / multi-step)
Legend: ├/└ = classified attributes of one request, evaluated together before routing.
ExampleScopeRoute
"How do I create a quiz?"KnowledgeRAG (Phase 2)
"How many students failed today's exam?"Analytics, freshTool / API (Phase 4)
"Write me a sorting algorithm"Out of domainRefuse

This classification is what every later routing decision (cache vs. RAG vs. tool, sync vs. async, agent vs. workflow) reads from — it's introduced now so nothing downstream has to re-invent it.

Architecture

User → QUE Service (FastAPI)
         ├─ Request Understanding (scope, intent, risk)
         └─ System prompt: identity + refusal rules
       → LLM
       → Response  (+ structured log: id, latency, tokens, scope)

Implementation Tasks

SYSTEM_PROMPT = """
You are QUE, the assistant embedded in Quizzer.
You answer questions about creating quizzes, taking exams,
viewing results, and using the platform.
You do not answer general knowledge, coding, or unrelated questions.
If a question is out of scope, say so directly and redirect
the user to what you can help with.
"""

Failure Cases

Can fail
Answers out-of-scope questions anyway; refuses legitimate questions; refusal message reads as robotic.
Security considerations
Refusal logic must not leak system prompt contents when probed; log storage must not capture secrets accidentally echoed by a user.

Metrics

Scope AccuracyFalse Refusal RateP95 Latency

Testing

Run the golden eval set on every prompt change. A scope-accuracy drop is a shipped regression, not a style choice — treat it the way you'd treat a broken unit test.

Trade-offs

You ship in days, not weeks. You give up grounding in real docs (Phase 2) and real data (Phase 4) — intentional, so the scope-and-identity layer is proven before anything depends on it.

Common Mistakes

  • Treating the refusal message as an afterthought — it's a UX surface people hit often early on.
  • Skipping the eval set "until there's more time" — there's no later phase that gets easier to add this in.
Do not add yet
RAG, tools, multiple agents, Kubernetes, a vector database. A domain-scoped chatbot with no retrieval is a legitimate, shippable V1.

Interview Perspective

How to explain it
"I started with the narrowest possible scope and put evaluation and logging in from the first commit, not after. That made every later regression attributable — if scope accuracy dropped after adding RAG, I knew immediately where to look, because I had a Phase 1 baseline to compare against."

After This Phase, You Should Be Able To Explain

QWhy build the Request Understanding layer before RAG or tools exist?
QWhy does evaluation start in Phase 1 instead of at the end of the project?
QWhat's the cost of a false refusal vs. a false acceptance, and how would you tune for one over the other?

Phase 2 — Knowledge System + Basic RAG

Stop trusting the model's memory of your product. Ground every knowledge answer in documents you control and can version.

0 / 0 tasks
LEARN→IMPLEMENT→TEST→MEASURE→DOCUMENT→SHIP

Objective

Build a retrieval pipeline over real Quizzer documentation so knowledge answers cite something real, not the model's training-time guess.

Why Now

Phase 1's assistant is confidently wrong about anything specific — button labels, current limits, recently changed workflows. RAG is the cheapest fix, and "how does this work" questions vastly outnumber data questions early on.

What You Will Build

  • An ingestion pipeline: parse → clean → chunk → embed → index.
  • A knowledge lifecycle that survives document updates, not just first ingestion.
  • Retrieval-quality evals layered onto the Phase 1 eval suite.

Concepts to Learn — Knowledge Lifecycle

Basic RAG tutorials stop at "index the docs." Production RAG has to survive the docs changing:

Document → Version → Parse → Chunk → Embed → Index → Active
                                                  │
                                          Update arrives
                                                  ▼
                                    Re-index new version → Active
                                                  │
                                          Retire old version
ConceptWhy it matters
Document versioningKnow which version of a doc a given answer was grounded in.
Incremental indexingRe-embedding the whole corpus on every doc edit doesn't scale.
Deletion propagationA retired doc must stop being retrievable, not just stop being updated.
Embedding versioningChanging embedding models means old and new vectors aren't comparable — re-index, don't mix.
Provenance / source metadataEvery chunk should carry back to a real source URL or doc ID for citation.

Architecture

Documents → Parsing → Cleaning → Chunking → Metadata → Embeddings → Index

Query time:
Question → Embed → Top-K Search → Context Assembly → LLM → Grounded Answer

API / Data Flow

QUE → Knowledge Base (vector search) → Answer
(no Quizzer backend call for a pure knowledge question)

Implementation Tasks

Failure Cases

  • Wrong document retrieved — semantically similar but factually irrelevant.
  • No relevant document — must say so, not fill the gap from training memory.
  • Outdated document served with full confidence — the freshness metadata from the lifecycle above is the fix.
  • Too much context diluting the model's attention on the one chunk that matters.

Security Considerations

Ingested documents are still untrusted content once retrieved — see Phase 10. Don't let document content be treated as instructions to the model.

Metrics

PrecisionRecall@KGrounded Answer RateNo-Answer Correctness

Testing

The labeled retrieval eval set becomes the seed of the Phase 11 unified evaluation platform — build it as a real artifact, not a one-off manual check.

Trade-offs

Grounding costs latency (a retrieval hop) and infrastructure (embeddings, a vector store, ingestion jobs). It buys answers actually about your product, with a citation trail.

Common Mistakes

  • Chunking by fixed character count with no regard for section boundaries.
  • No freshness or version metadata — impossible to tell if a retrieved answer is current.
Do not add yet
Hybrid search, reranking, query rewriting. Plain dense retrieval with sane chunking proves the pipeline first — add fusion in Phase 6 once evidence shows dense-only is missing things.

Interview Perspective

How to explain it
"I built the ingestion pipeline — including versioning and provenance — before touching retrieval quality, because garbage chunking makes every retrieval metric meaningless, and an answer with no traceable source isn't actually grounded, just lucky."

After This Phase, You Should Be Able To Explain

QWhy did you introduce RAG instead of fine-tuning on Quizzer documentation?
QWhat happens when retrieval returns an irrelevant document, end to end?
QHow do you know an answer is actually grounded rather than coincidentally correct?
QHow does document versioning prevent a stale answer from being served with confidence?

Phase 3 — Context Engineering

Stop asking questions the application already knows the answer to.

0 / 0 tasks
LEARN→IMPLEMENT→TEST→MEASURE→DOCUMENT→SHIP

Objective

Feed QUE the user's current page, entity, role, and running conversation, so it resolves "how many students failed?" without a clarifying round-trip.

Why Now

RAG answers "how does grading work," not "how did this exam do" — the majority of real usage once QUE is embedded in the product. Context has to exist before Phase 4's tools, or every tool call becomes a round-trip asking the user to repeat what the UI already knows.

Current State → Next State

Current systemDomain-scoped, grounded assistant with no awareness of what the user is looking at
ProblemAmbiguous questions require a clarifying round-trip the UI could have avoided
New capabilityStructured page/entity/role context resolves pronouns and implicit references
Architecture changeFrontend sends a structured context object alongside every message
New trade-offContext becomes a new surface to validate — it's a UX hint, never a security boundary

Architecture

{
  "message": "How many students failed?",
  "context": {
    "current_page": "exam_results",
    "current_exam_id": 123,
    "user_role": "teacher"
  }
}
→ QUE resolves "students" to exam 123's roster,
  "failed" to below that exam's passing threshold,
  without asking "which exam?"

Implementation Tasks

Failure Cases

  • Stale page context (user navigated away) causes an answer about the wrong exam.
  • Context injected as free text gets mixed up with user-authored content — a prompt-injection surface.

Security Considerations

A student's role claim in context must still be verified server-side — Phase 3 context is a UX convenience, and Phase 5's policy engine is the actual security boundary.

Metrics

Clarifying-Question RateContext Resolution Accuracy

Trade-offs

Better UX and fewer round-trips, at the cost of a context object that must be kept honest and re-verified, never trusted outright.

Common Mistakes

  • Letting page context silently override explicit conversation history.
  • Treating client-supplied role as sufficient for authorization.
Do not add yet
Long-term user memory or cross-session personalization — context here is per-request and per-conversation, not a persistent profile.

Interview Perspective

How to explain it
"I kept context in structured fields the frontend controls explicitly, rather than folding it into prompt text — that made it easy to reason about what the model could trust, and trivial to strip a field at the gateway if it ever became a risk."

After This Phase, You Should Be Able To Explain

QWhy is page context passed as structured fields instead of embedded in the prompt text?
QWhy can't client-supplied role be trusted for authorization?

Phase 4 — Tools + Secure Tool Execution + Workflows

Give the model a fixed set of controlled actions — and decide, per feature, whether it even needs to be the model choosing at all.

0 / 0 tasks
LEARN→IMPLEMENT→TEST→MEASURE→DOCUMENT→SHIP

Objective

Let QUE answer data questions through a small, explicit tool registry backed by real Quizzer internal APIs — never a raw query — and formalize when a fixed sequence beats a model-driven loop.

Why Now

RAG answers product questions; it can't answer "how did this user's data look," because that data isn't in any document. Tools are the bridge, introduced now because Phase 3's context resolves most of their arguments automatically.

Concepts to Learn — Workflow vs. Agent

Not every AI feature needs an autonomous loop. Decide explicitly:

Deterministic workflow
Use when the steps are known in advance. 
Fetch data → Validate → Analyze
→ Generate report → Store result
Agentic workflow
Use when the next step depends on a model decision. 
Understand request → choose capability
→ choose tool → inspect result
→ decide next action → continue/finish

A single Quizzer tool call ("what's my score?") is a workflow, not an agent loop — there's no decision to make after the fetch. Save the agent loop (Phase 7) for requests where the next step genuinely depends on what the previous tool returned.

Concepts to Learn — Human-in-the-Loop

Not every action should execute automatically just because a tool exists for it:

READ              → execute automatically
LOW-RISK WRITE    → execute if policy allows
HIGH-RISK WRITE   → confirmation required
CRITICAL ACTION   → explicit confirmation + audit log
ActionRisk tier
View resultsRead
Draft a quiz (not published)Low-risk write
Publish an examHigh-risk write — confirm
Delete content, send notificationsCritical — confirm + audit

Concepts to Learn — Idempotency

Any write-capable tool must be safe to retry:

request → idempotency key → operation → safe retry
(same key + same request = same result, never a duplicate)

Without this, a client retry after a timeout can silently create two quizzes or send a notification twice — the retry succeeding is not the same as the retry being safe.

Architecture

explain_exam_status / summarize_exam_results / diagnose_publish_blockers
… (14 read-only insight tools — docs/TOOL_CONTRACTS_V1.md)

QUE → deterministic select → POST /internal/que/v1/tools/invoke
    → ownership check → structured envelope → TOOL_RESULT → generate

Implementation Tasks

{
  "name": "count_students_below_score",
  "description": "Count students who scored below a threshold on an exam",
  "parameters": {"exam_id": "integer", "threshold": "number"},
  "requires_role": ["teacher", "admin"],
  "risk_tier": "read",
  "timeout_ms": 3000,
  "idempotency_required": false
}

Failure Cases

  • Tool timeout — Quizzer's internal API is slow or down; degrade gracefully.
  • Invalid tool result not matching the expected schema.
  • Retried write without an idempotency key creates a duplicate.

Security Considerations

Every tool is read-only in V1. Confirmation requirements are enforced server-side, never inferred from the model's own claim that it "asked the user first."

Metrics

Tool Selection AccuracyTool Argument AccuracyTool Failure RateUnconfirmed High-Risk Attempts

Trade-offs

Narrow, read-only tools mean a slower rollout of "write" features, but they bound the worst case: even a fully hallucinating model can only call a function you've already reviewed.

Common Mistakes

  • Building one large "do anything" tool instead of several narrow ones.
  • Skipping idempotency because "writes aren't built yet" — retrofitting it later touches every write tool at once.
Do not add yet
Unlimited tool chaining, write-capable tools beyond low-risk drafts, or a general "run arbitrary query" tool.

Interview Perspective

How to explain it
"I default to a deterministic workflow and only reach for an agent loop when the next step genuinely can't be known in advance. Most 'AI features' people imagine as agents are actually a fixed three-step workflow with an LLM doing the summarizing at the end."

After This Phase, You Should Be Able To Explain

QHow do you decide whether a feature is a deterministic workflow or an agentic loop?
QWhy does a retried write request need an idempotency key?
QWhat's the difference between a tool the model can call and an action the system will actually execute?

Phase 5 — Identity + Permissions + Capabilities + Policy

Authentication, authorization, and policy are three different questions. Answer them in three different places.

0 / 0 tasks
LEARN→IMPLEMENT→TEST→MEASURE→DOCUMENT→SHIP

Objective

Wire the authenticated user's real identity and role into tool selection through an explicit policy engine, so capability is enforced, not just data filtered after the fact.

Why Now

Phase 4 built tools; it didn't guarantee a student can't call a teacher-only tool. Once tools exist, permission enforcement is the very next thing that has to exist — shipping tool-calling without it is shipping a data-leak generator.

Concepts to Learn — Auth vs. Authorization vs. Policy

LayerQuestion it answers
AuthenticationWho are you?
AuthorizationWhat can you access?
PolicyUnder what conditions can you perform this specific action, right now?

A policy engine sits above simple role checks and owns: capability permissions, tool permissions, resource access, sensitive-operation gating, confirmation requirements (from Phase 4), data boundaries, and — where relevant — tenant boundaries (Phase 18).

Architecture

Student:  get_my_results()
Teacher:  get_class_results(), get_exam_statistics()
Admin:    get_platform_statistics()

Defense in depth:
Application Validation + Authorization + Tool Constraints
+ AI Guardrails + Output Validation
— no single layer is trusted alone

Implementation Tasks

Failure Cases

  • Role spoofing via client-supplied context (why Phase 3 context must be re-verified server-side).
  • A correctly-scoped tool result leaking other students' names in free text.
  • Privilege escalation through a chained tool call reaching data outside the caller's scope.

Security Considerations

Treat the model's tool choice as a suggestion, never a grant. The real check happens in three independent places: prompt-level instruction, tool registry filtering, and the backend API.

Metrics

Unauthorized Requests BlockedPermission Test Pass Rate

Trade-offs

Explicit per-tool checks are more code up front than a shared role flag, but they're auditable — you can point to exactly which line decided a request was allowed.

Common Mistakes

  • Trusting the model's own statement that it checked permissions.
  • Filtering tool results for role but not the free-text summary wrapped around them.
Do not add yet
A generic RBAC framework or full multi-tenant policy engine before you have more than 3 roles. Explicit per-tool checks are enough until the matrix gets genuinely unwieldy.

Interview Perspective

How to explain it
"I separated policy from authorization explicitly — authorization says what a teacher can generally access, policy decides whether this specific call, with this specific confirmation state, is allowed right now. That separation is what let confirmation requirements from the tools phase plug in cleanly instead of becoming ad hoc if-statements."

After This Phase, You Should Be Able To Explain

QWhat's the difference between authorization and policy in your system?
QWhy is the model's tool selection never treated as an authorization decision?
QHow would tenant boundaries extend this policy engine if Quizzer became multi-tenant?

Phase 6 — Retrieval Evolution: Hybrid Search

Dense + BM25 RRF shipped after eval evidence; neural cross-encoder deferred.

0 / 0 tasks
LEARN→IMPLEMENT→TEST→MEASURE→DOCUMENT→SHIP

Objective

Combine dense and sparse retrieval, fuse the results, and rerank before context reaches the model.

Why Now

Dense retrieval is strong on "similar meaning," weak on exact terms — error codes, feature names, IDs. If the Phase 2 eval set shows misses clustered on exact-term queries, that's the evidence this phase responds to.

Architecture

Query
  ├── Dense Search (embeddings)
  └── Sparse / Keyword Search (BM25)
         │
         ▼
    Result Fusion (reciprocal rank fusion)
         │
         ▼
     Reranking (cross-encoder)
         │
         ▼
  Deduplication + Context Compression → Best Context

Implementation Tasks

Failure Cases

  • Fusion weights tuned for one query type regress another — always test the full eval set.
  • Reranking latency violates the P95 budget if the cross-encoder isn't small enough.

Metrics

Recall@K delta vs. Phase 2P95 Retrieval Latency

Trade-offs

Better recall on exact-term queries, at the cost of a second search system to maintain and a reranking hop to budget for.

Deferred
Neural cross-encoder rerank (p6-t3) — recall already improved with RRF; add CE only if a new miss cluster needs it and P95 allows.

Interview Perspective

How to explain it
"I only introduced hybrid search after the eval set showed a specific pattern — exact-term queries dense retrieval consistently missed. That gave me a measurable before/after instead of 'this should help.'"

After This Phase, You Should Be Able To Explain

QWhy dense search before hybrid search?
QWhat specific evidence justified adding sparse retrieval?

Phase 7 — Agent Runtime

Explicit workflow-vs-agent routing and a bounded multi-tool loop over the Phase 4/5 tool set — not ReAct.

0 / 0 tasks
LEARN→IMPLEMENT→TEST→MEASURE→DOCUMENT→SHIP

Objective

Build the runtime that decides, per request, whether to run a deterministic workflow or an agent loop — and bounds the loop when it runs one.

Why Now

Phase 4 introduced single tool calls; real usage eventually produces requests needing more than one — "compare this exam to last month's, and tell me which topics got worse." That needs a controlled loop, introduced only once single-tool-call tools are proven (Phase 4) and permission-scoped (Phase 5).

Request Understanding (Phase 1)

      ▼
Workflow-or-Agent Decision
      │
 ┌────┴────┐
 ▼         ▼
Workflow   Agent Loop
(fixed     (choose capability → choose tool

              MAX_AGENT_STEPS)

Implementation Tasks

Failure Cases

  • Infinite or slow-converging loops burning cost and time.
  • A loop that "finishes" with a wrong answer built on a misread intermediate tool result.

Metrics

Avg. Steps per Agentic RequestLoop Termination Reason (converged / step-limit / timeout)

Trade-offs

The loop handles genuinely multi-step questions well, but every additional step is additional latency, cost, and chance for a wrong intermediate decision to compound.

Common Mistakes

  • Defaulting every feature to the agent loop because it's already built — most requests are still workflows.
Do not add yet
Planning/reflection loops, memory across sessions, or multi-agent coordination. A single bounded loop over the Phase 4/5 tool set is enough until there's evidence otherwise (Phase 17).

Interview Perspective

How to explain it
"The runtime makes workflow-vs-agent an explicit decision per request type, logged and revisitable — not a default everything routes through. That kept the majority of traffic on the cheaper, more predictable workflow path."

After This Phase, You Should Be Able To Explain

Phase 8 — LLM Gateway + Model Routing

Stop hard-coding one provider into every call site. Route by complexity, cost, and availability.

0 / 0 tasks
LEARN→IMPLEMENT→TEST→MEASURE→DOCUMENT→SHIP

Objective

Introduce a thin abstraction between QUE and whichever provider serves a request, so model choice is a routing decision, not a code change.

Why Now

By this phase you have real traffic data: simple scope checks vs. multi-tool reasoning. Paying frontier prices for "how do I create a quiz?" is now a measurable waste — that's the trigger, not "gateways are best practice."

Architecture

QUE Agent → LLM Gateway (OpenRouter, OpenAI-compatible)
              ├── openai/gpt-4o-mini          (preferred on agent / multi_step)
              ├── google/gemma-4-31b-it:free
              └── nvidia/nemotron-3.5-lightning:free
Round-robin keys (LLM_API_KEY + LLM_API_KEY_N) and models.
Failover: next key, then next model. Cap 3 attempts + backoff.
Stream: do not splice two models into one SSE reply.

Implementation Tasks

Failure Cases

  • Provider outage with no fallback takes down the whole agent.
  • Silent quality regression when a fallback model handles something the primary would've done better.
  • Retry storms amplifying an outage instead of absorbing it.

Metrics

Cost per RequestFallback RateP95 Latency by Route

Trade-offs

An abstraction layer to maintain, in exchange for provider resilience and a lever to cut cost without a code change.

Did not add
Native multi-provider SDKs, per-user sticky sessions, or cost accounting beyond model + latency logs. Embeddings stay off the chat round-robin.

Interview Perspective

How to explain it
"The gateway exists because cost and latency data showed most requests didn't need the frontier model. Routing on measured complexity cut cost per request without moving the eval-suite quality numbers."

After This Phase, You Should Be Able To Explain

QWhat signal drives the routing decision between a cheap and an expensive model?
QWhat happens to in-flight requests during a provider outage?

Glossary

Short definitions for terms used throughout this handbook.

RAG

Retrieval-augmented generation — grounding a model's answer in retrieved documents instead of its training memory.

Embedding

A numeric vector representing the meaning of a piece of text, used for similarity search.

Vector search

Finding the nearest embeddings to a query embedding, used to retrieve relevant chunks.

Reranking

A second, more accurate pass over a retrieval shortlist to reorder by true relevance.

Inference

A single forward pass through the model producing a response — a network call, not a function call.

Context window

The maximum tokens a model can attend to in one call; prompt, history, and retrieved context share this budget.

Tool calling

The model requesting execution of a predefined, schema-validated function rather than free text.

Agent loop

A bounded cycle of choose-tool → inspect-result → decide-next-action, used when steps aren't known in advance.

Idempotency

A property where repeating the same request with the same key produces the same result, never a duplicate side effect.

P95 / P99

The latency below which 95% / 99% of requests complete — captures the tail a mean hides.

Circuit breaker

Stops calling a dependency that's already failing, instead of piling retries onto an outage.

Prompt injection

An attempt to override a model's instructions via crafted input, directly or via retrieved/tool content (indirect injection).

Multi-tenancy

Serving multiple isolated customer organizations from one system, with strict data and permission boundaries per tenant.

Semantic cache

A cache keyed by meaning-similarity of a query rather than an exact string match.
